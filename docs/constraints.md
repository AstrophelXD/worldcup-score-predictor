# 世界杯指定场次比分预测系统约束与边界

本文档定义项目实施过程中必须遵守的业务口径、数据边界、工程约束和建模约束，避免后续出现“训练和展示口径不一致”“赛后信息泄漏”“UI 和模型耦合过深”等问题。

## 1. 预测口径约束

### 1.1 默认预测目标

- 默认预测对象为 **90 分钟常规时间最终比分**。
- 不包含加时赛结果。
- 不包含点球大战结果。
- 所有主指标、回测指标、dashboard 展示默认都基于 90 分钟比分。

### 1.2 淘汰赛处理

- 淘汰赛场次仍以 90 分钟比分作为主标签。
- 可额外保留 `aet_score`、`penalty_score` 字段，但不得混入主标签。
- 如未来扩展“晋级概率”或“120 分钟结果”，必须新增独立任务定义和独立输出头，不得复用当前主标签。

### 1.3 小组赛与淘汰赛差异

- 小组赛允许平局，且存在积分驱动行为。
- 淘汰赛 90 分钟后存在加时赛可能，导致部分球队在常规时间更保守。
- 建模时允许将 `stage_type`、`must_win_flag`、`draw_acceptable_flag` 作为特征，但不得改变主标签定义。

## 2. 输出约束

系统必须能够稳定输出以下内容：

1. 概率最高的 3 个具体比分及其概率。
2. 胜 / 平 / 负概率。
3. Over / Under 2.5 概率。
4. BTTS（双方进球）概率。
5. 期望进球数。
6. 模型不确定性或置信度。
7. `0-7 × 0-7` 的比分概率矩阵。

### 2.1 概率一致性约束

- 所有衍生输出必须从统一的比分联合概率分布聚合得到。
- 不允许单独训练一个 1X2 分类模型后直接覆盖比分矩阵聚合结果。
- 若采用多头损失训练，最终 serving 输出仍以联合矩阵为主，分类头仅作为训练辅助或校准参考。

### 2.2 比分矩阵约束

- UI 默认展示 `0-7 × 0-7` 网格。
- 如模型内部保留 `>7` 的尾部质量，需单独记录 `overflow_prob`。
- 面向业务展示时，不得静默丢弃尾部概率后不做说明。

## 3. 数据边界约束

### 3.1 数据分层

项目数据层必须分为以下三层：

- `raw`：原始抓取数据，不做语义改写。
- `curated`：标准化、可关联的实体表和事实表。
- `feature_mart`：按时间点构造的训练/推理特征视图。

### 3.2 数据来源等级

- `v0`：公开数据 + 手动数据，必须可独立跑通。
- `v1`：可选加入赔率、Elo、FIFA ranking。
- `v2`：可选加入球员级特征、预计首发、伤停。
- `v3`：可选加入事件数据和 xG。
- `v4`：可选加入实时数据刷新和正式首发重跑。

### 3.3 来源可追溯性

每张核心表都必须包含：

- `source_system`
- `source_record_id`
- `ingested_at`
- `updated_at`

任何经手动修改的记录都必须额外记录：

- `is_manual_override`
- `override_reason`
- `override_by`
- `override_at`

## 4. 反未来信息泄漏约束

本项目最重要的硬约束之一是 **不得在训练或回测中使用预测时点之后才知道的信息**。

### 4.1 时间点定义

每次训练样本和推理请求都必须绑定一个明确的 `as_of_time`。

### 4.2 明确禁止使用的信息

- 比赛结束后的任何统计。
- 开赛后才确认的正式首发用于赛前预测版本。
- 开赛后更新的赔率快照用于赛前预测版本。
- 赛后修正后的球员状态直接回填到赛前特征。
- 使用未来比赛更新后的 Elo/FIFA 排名去回测更早比赛。

### 4.3 Point-in-time join 约束

- 特征构建器必须显式以 `match_kickoff_ts` 或 `prediction_ts` 做截止。
- 所有滚动窗口统计只能聚合截止时间之前的比赛。
- 所有外部快照表都必须可按时间过滤，不允许只保留“最新一份”。

## 5. 建模约束

### 5.1 模型路线约束

项目至少维护三层模型路线：

- Baseline：Elo + Poisson / Dixon-Coles
- Mid-level：tabular + player aggregation
- Advanced：Temporal Transformer + Player Set Transformer + Matchup Encoder + Mixture Score Head

### 5.2 基线模型不可移除

- 无论高级模型进展如何，baseline 必须长期保留。
- baseline 作为：
  - 快速回归检查
  - 数据质量报警参照
  - 高级模型异常时的 fallback

### 5.3 高级模型上线门槛

高级模型只有在以下条件满足后才可作为默认模型：

- 在严格时间回测中优于 baseline。
- 概率校准不弱于 baseline。
- 对关键页面响应时间可接受。
- 对缺失数据输入具有可解释的降级行为。

## 6. 评估与回测约束

### 6.1 切分方式

- 只能按时间切分训练 / 验证 / 测试。
- 禁止随机打散切分作为主回测依据。

### 6.2 世界杯专项测试

- 2018 世界杯和 2022 世界杯必须作为独立 out-of-time 测试集进行回测。
- 回测时只能使用比赛开赛前可得信息。

### 6.3 最低评估指标

每个模型版本至少产出以下指标：

- score NLL
- top-3 scoreline hit rate
- 1X2 Brier score
- OU2.5 Brier score
- BTTS Brier score
- Ranked Probability Score
- calibration curve / ECE

## 7. Dashboard 约束

### 7.1 前后端边界

- dashboard 不直接依赖训练内部对象。
- dashboard 仅通过 API 访问预测、特征和回测结果。

### 7.2 核心页面

MVP 至少应包括：

- Match Selector
- Prediction Summary
- Score Matrix Heatmap

后续扩展页面：

- Team Comparison
- Player Availability / Lineup
- Explanation
- Backtesting
- Data Freshness

### 7.3 展示口径统一

- 页面展示的 1X2、OU2.5、BTTS 概率必须与 API 返回一致。
- 若用户修改手工首发或伤停，必须标注该预测为 override 版本。

## 8. 工程与部署约束

### 8.1 技术栈边界

- 训练框架以 Python + PyTorch 为主。
- 推理服务以 FastAPI 为主。
- MVP dashboard 建议 Streamlit。
- 模型与特征处理逻辑不得散落在 dashboard 页面脚本中。

### 8.2 模块化约束

代码必须至少拆为：

- `data_ingestion`
- `features`
- `models`
- `training`
- `inference`
- `api`
- `dashboard`

### 8.3 可替换性约束

- 数据源适配层需独立，便于以后替换 API-Football / StatsBomb / 手动 CSV。
- 模型 registry 与 checkpoint 管理需独立，不与某一模型类强绑定。

## 9. 手动数据约束

允许维护以下手工输入：

- 临场伤停
- 预计首发概率
- 教练阵型倾向
- 战术备注

但必须满足：

- 保留原始值和修改值
- 记录修改人和时间
- 可在 dashboard 中追溯

## 10. 性能与硬件约束

### 10.1 执行环境

- 训练、回测、GPU 推理等重计算任务在 **具备 CUDA 与足够显存的环境** 中执行。
- 日常开发可进行代码编写、文档、静态检查与不依赖 GPU 的轻量验证。
- 文档与自动化助手应给出可复制执行的完整命令与步骤，并说明资源需求与预期产物。

### 10.2 训练假设

- 目标环境为单机单卡 GPU；显存需求因模型而异（Baseline 较低，ScoreGen 建议 16GB+）。
- 默认启用 mixed precision。
- 高级模型应优先适配单卡训练。

### 10.3 Serving 约束

- 单场预测响应时间目标：
  - baseline：< 1 秒
  - mid-level：< 2 秒
  - advanced：< 5 秒

### 10.4 训练资源约束

- 优先支持单机单卡。
- 多卡训练不是 MVP 必需项。

## 11. 文档与变更管理约束

- 每新增数据源、特征组、模型版本，都要更新对应设计文档。
- 每次改变预测口径时，必须同步更新本约束文档。
- 若系统从“90 分钟预测”扩展到“晋级概率预测”，必须新增独立文档，不应在当前文档中隐式混用。
